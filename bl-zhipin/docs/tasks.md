状态：T01～T16 已实现并完成验收。验收日期为 2026-10-27，执行结果及逐项证据见 [验收记录](verification.md)。

## 实现约定

- 后端建议采用 FastAPI，使用 Python `sqlite3` 操作 SQLite；前端使用 HTML、CSS、原生 JavaScript，通过 `fetch` 调用 `/api/` 接口。
- 一个 Python 服务提供页面、静态资源和 API，采用同源访问；简历通过鉴权下载接口获取，不放进公开静态目录。
- 页面与 API 按账号、岗位、招聘、投递、邀请、预约划分。下文的文件和接口名称是建议组织方式，可在保持业务行为一致的前提下调整。
- 成功响应返回 JSON，输入错误、未登录、无权限、记录不存在、业务冲突分别使用明确的 HTTP 状态码和中文提示；普通 HTML 页面访问与文件下载除外。
- 所有权限与业务限制在后端执行；前端隐藏按钮仅用于改善操作体验。
- 数据与简历保存在 `bl-zhipin/data/`，不提交 Git。测试使用独立临时数据库和目录，不操作真实用户数据。
- 时间以带时区的时间点处理和保存，页面统一显示北京时间 `Asia/Shanghai`；“7 天”从邀请生成时开始计算。
- 每项任务的功能、接口、页面及其验收条件均完成后，才能勾选对应任务。

FastAPI 的静态资源与文件上传方案分别参考[静态文件文档](https://fastapi.tiangolo.com/tutorial/static-files/)和[文件上传文档](https://fastapi.tiangolo.com/tutorial/request-files/)；数据库连接和事务参考 [Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html)。

## 第一阶段：基础能力

### T01：项目骨架与本地服务

**功能**：建立可启动的 Python 服务，并能访问 HTML 页面和 API。

**实现方式**：

- 创建 `app/`、`app/api/`、`app/services/`、`static/`、`tests/` 等目录，业务代码限定在 `bl-zhipin/`。
- 建立应用入口、依赖清单、配置读取和启动命令，锁定实际验证过的依赖版本。
- 挂载静态资源并提供页面路由，API 统一使用 `/api/` 前缀，增加健康检查接口。
- 建立项目内 `.gitignore`，忽略虚拟环境、数据库及其日志、上传文件、测试产物和本地配置。

**验收条件**：

1. 按依赖清单安装后，使用一条启动命令能运行服务。
2. 同一地址可访问 HTML 首页、CSS、JavaScript 和健康检查接口。
3. 数据库和上传目录不通过静态资源路由公开。
4. 项目新增运行产物被 Git 忽略，不影响同级 `oa/` 内容。

### T02：数据库与本地数据目录

**功能**：持久化账号、岗位、招聘、投递、邀请和预约数据。

**实现方式**：

- 建立 `users`、`companies`、`sessions`、`positions`、`jobs`、`applications`、`invitations`、`appointments` 等表。
- 公司与公司账号一一对应；招聘关联公司和岗位；投递关联招聘和求职者；邀请关联投递；预约关联邀请。
- 公司名称和岗位名称分别保存展示值、标准化唯一值；标准化规则为去除首尾空格并忽略英文大小写。
- 用户名、标准化公司名、标准化岗位名、求职者与招聘的投递组合、邀请与预约的对应关系建立唯一约束。
- 启用外键约束，参数化执行 SQL；建立幂等初始化流程和明确的事务边界。
- 记录创建时间、招聘开放状态、投递查看时间、邀请失效时间及撤销或使用时间。

**验收条件**：

1. 空目录首次启动可创建数据库，重复初始化不清空已有数据。
2. 数据库约束能阻止重复公司、重复岗位、重复投递及同一邀请多次预约。
3. 注册、投递和预约等多步写入发生异常时整体回滚，不留下半条业务记录。
4. 重启服务后数据和简历引用仍可读取。

### T03：注册、登录、退出与管理员初始化

**功能**：支持求职者和公司注册，提供三个角色的登录与访问控制。

**实现方式**：

- 提供注册、登录、退出、当前账号接口，如 `/api/auth/register`、`login`、`logout`、`me`。
- 注册表单选择角色；公司角色必须填写公司名称，注册时在事务内建立公司和账号。
- 密码使用带随机盐的密码哈希保存；使用服务端会话和 HttpOnly、SameSite Cookie，退出时使会话失效。
- 实现登录检查、角色检查和资源归属检查，供后续接口复用；对会话保护的写入请求校验同源或 CSRF 凭证。
- 提供管理员初始化命令，公开注册接口仅接受求职者、公司两种角色，禁止注册后修改角色。

**验收条件**：

1. 求职者、公司均能注册、登录、退出，刷新页面仍能正确识别当前账号。
2. 公司名称为空或重复、用户名重复时注册失败，数据库不残留关联记录。
3. ` ACME ` 与 `acme` 不能注册成两家公司。
4. 伪造管理员角色、修改角色、使用退出后的会话均不能获得权限。
5. 管理员可以通过命令创建并登录，数据库不保存明文密码。

### T04：公共页面布局与前端 API 客户端

**功能**：提供一致的中文蓝白界面和前端交互基础。

**实现方式**：

- 建立公共导航、内容区域、表单、列表、按钮、提示和状态标签样式，适配桌面和手机宽度。
- 封装 JSON 请求、文件表单请求、会话状态及 API 错误提示。
- 按角色显示导航与操作入口，统一处理未登录、加载中、空列表和提交中状态。
- 使用安全的文本渲染方式展示公司名称、岗位介绍等用户输入。

**验收条件**：

1. 主要页面为中文，蓝白配色一致，手机宽度下表单和主要按钮可正常操作。
2. API 返回错误时显示可理解的提示，提交失败后保留已填写的普通表单内容。
3. 页面加载、重复点击和会话失效有明确反馈。
4. 公司名称或岗位介绍中的 HTML 字符以文本呈现，不执行脚本。

## 第二阶段：招聘业务

### T05：管理员岗位目录管理

**功能**：管理员新增、改名、停用岗位名称。

**实现方式**：

- 提供管理员岗位列表、新增、改名、停用接口及对应管理页面。
- 服务端规范化岗位名称并检查唯一性，数据库唯一约束处理同时新增的情况。
- 通过岗位关联查询显示名称，改名后关联招聘同步显示新名称；停用仅影响新招聘的选择。

**验收条件**：

1. 管理员能新增、改名和停用岗位；普通用户、公司和访客均不能调用管理接口。
2. 空名称及仅空格名称不能提交，首尾空格或英文大小写不同的重名岗位不能重复新增。
3. 岗位改名后，关联招聘显示新名称。
4. 停用后不能以该岗位发布新招聘，已有招聘和投递仍然保留。

### T06：公司招聘需求管理

**功能**：公司发布、编辑、关闭、重新开放自己的招聘需求。

**实现方式**：

- 提供公司招聘列表、发布、编辑、关闭和重新开放接口及 HTML 管理页面。
- 发布时选择有效岗位并填写岗位介绍、联系邮箱，后端从当前会话取得公司身份。
- 查询和更新均按当前公司过滤资源；关闭只变更状态，不删除招聘、投递和邀请数据。
- 岗位停用后仍允许保留既有招聘的岗位引用，编辑时若改选岗位则必须选有效岗位。

**验收条件**：

1. 公司能使用有效岗位发布招聘，岗位介绍和邮箱必填，邮箱格式错误时拒绝提交。
2. 求职者、管理员和访客不能发布招聘；公司不能编辑其他公司的招聘。
3. 招聘关闭后不出现在公开招聘列表中，也不能接收新投递；重新开放后恢复。
4. 关闭前的投递、简历、邀请及预约记录仍可按原权限读取。
5. 界面和 API 不提供删除招聘入口。

### T07：招聘公开浏览、搜索与筛选

**功能**：访客浏览开放招聘、查看详情、搜索和按岗位筛选。

**实现方式**：

- 提供公开招聘列表和详情接口，以及列表、详情 HTML 页面。
- 搜索匹配岗位名称、公司名称或岗位介绍；岗位筛选与关键词可组合使用。
- 仅返回开放招聘，详情展示公司名称、岗位名称、岗位介绍、联系邮箱和投递入口。
- 已关闭详情的公开访问返回明确的不可投递提示，不暴露内部投递数据。

**验收条件**：

1. 未登录用户能浏览开放招聘和联系邮箱。
2. 搜索、筛选、组合查询及清空条件均返回正确结果，无结果时显示空状态。
3. 公司编辑招聘或岗位改名后，公开详情展示最新信息。
4. 未登录点击投递时引导登录，已登录求职者可进入投递流程。

### T08：简历上传与投递

**功能**：求职者提交个人资料及 PDF、DOC、DOCX 简历。

**实现方式**：

- 使用 `multipart/form-data` 一次提交姓名、联系邮箱、可选手机号和简历，避免产生未绑定投递的公开上传入口。
- 服务端检查求职者身份、招聘开放状态、重复投递、字段有效性、文件扩展名和基本文件格式。
- 按实际读取的字节数限制单文件不超过 10 MB；文件以随机名称保存在私有目录，原始名称仅作显示和下载用途。
- 写入投递时保留姓名、邮箱、手机号及简历的提交快照；失败时清理临时文件，重复约束放在数据库中。
- 不提供修改、撤回或替换投递资料的接口。

**验收条件**：

1. 合法 PDF、DOC、DOCX 均可投递，姓名或邮箱缺失、格式错误时提示原因；手机号可留空。
2. 空文件、超限文件、不支持的类型及明显伪装成简历的文件被拒绝，不留下无主文件。
3. 同一求职者对同一招聘只能成功投递一次，同时重复提交也只能生成一条记录。
4. 公司、管理员、访客不能投递，已关闭招聘不能投递。
5. 修改账号资料不会改写已提交的资料快照，无法通过 URL 直接访问简历文件。

### T09：公司查看投递与下载简历

**功能**：公司查看收到的投递、打开详情、下载简历。

**实现方式**：

- 提供公司投递列表、投递详情、简历下载接口及页面，按当前公司关联的招聘查询。
- 打开详情时记录查看时间，将投递展示状态从“已投递”更新为“已查看”；列表查询本身不标记已查看。
- 简历下载先校验登录、角色和投递归属，再以附件形式返回文件，安全处理下载文件名。

**验收条件**：

1. 公司能查看自己招聘收到的资料和简历名称，下载文件与上传内容一致。
2. 只打开列表不改变状态，打开详情后求职者看到“已查看”。
3. 修改投递 ID 或下载 ID 不能读取其他公司的资料；管理员也不能下载简历。
4. 文件缺失或记录不存在时显示明确提示，不泄露本地文件路径。

### T10：求职者投递历史

**功能**：求职者查看自己的投递记录和查看状态。

**实现方式**：

- 提供当前求职者的投递列表与详情接口，以及“我的投递”页面。
- 展示公司、岗位、投递时间、原始投递资料和“已投递／已查看”状态。
- 即使招聘关闭或岗位停用，仍通过历史关联保留投递记录；为后续邀请和预约结果保留展示位置。

**验收条件**：

1. 求职者只能查看自己的投递，直接调用其他用户的详情接口同样失败。
2. 公司查看前后，投递状态能正确变化。
3. 招聘关闭、岗位停用后历史投递仍可访问，空列表有明确提示。

## 第三阶段：邀请与预约

### T11：专属邀请链接生成、撤销与重发

**功能**：公司针对收到的投递生成邀请，求职者查看链接，公司可复制、撤销和重发。

**实现方式**：

- 提供按投递生成邀请、查询邀请及撤销接口，生成随机且不可预测的凭证，关联投递和生成时间。
- 有效期为生成后 7 天；展示“待预约／已预约／已失效／已撤销”状态。
- 待预约期间重复生成操作返回当前有效邀请；只有失效或撤销后才生成新的邀请记录和凭证。
- 公司投递详情提供生成、复制、撤销入口，求职者自己的投递记录显示邀请链接。
- 重发保留旧邀请失效状态，原链接不能恢复；不集成邮件、短信发送服务。

**验收条件**：

1. 公司只能给自己收到的投递生成或撤销邀请，求职者和管理员不能调用该操作。
2. 求职者仅能从自己的投递记录取得邀请，公司复制的链接可直接打开对应表单。
3. 生成后未满 7 天且未使用、未撤销时有效，到期立即不能提交。
4. 撤销或失效后重发获得新链接，旧链接始终无效。
5. 已成功预约的邀请不能撤销或重发成第二份预约。

### T12：免登录预约表单与提交

**功能**：通过邀请链接填写姓名、手机号、预约时间并完成预约。

**实现方式**：

- 提供 `/invite/{token}` HTML 页面，以及查询邀请可用性、提交预约的公开 API。
- 有效页面仅展示必要的公司、岗位和表单信息，不返回投递中的既有姓名、邮箱、手机号或简历。
- 姓名、手机号、未来预约日期时间必填；明确按北京时间解释表单时间，后端统一转换并校验。
- 使用数据库事务和预约唯一约束，在一次提交中完成邀请有效性检查、预约写入和邀请使用状态更新。
- 不要求登录，不增加公司审批、可约时段或同一时间人数限制。

**验收条件**：

1. 无痕窗口或退出登录后仍可通过有效链接预约。
2. 必填项为空、手机号无效、预约时间等于或早于当前时间时提交失败。
3. 生成时间满 7 天、已撤销、已使用、随机无效链接均不能提交，页面显示明确状态。
4. 同一链接重复点击或同时提交，只产生一条预约。
5. 不同邀请可以选择同一公司相同时间，均能成功预约。
6. 页面和公开 API 均不包含求职者已有个人资料、简历地址或其他人的预约信息。

### T13：公司预约管理与求职者结果展示

**功能**：公司查看预约结果，求职者在投递记录中查看自己的邀请与预约状态。

**实现方式**：

- 公司预约列表、详情查询通过投递和招聘关联验证公司归属，展示公司收到的预约姓名、手机号、时间及对应岗位。
- “我的投递”展示邀请状态和预约结果，保持投递查看状态与邀请状态分别显示。
- 所有时间统一显示北京时间，重新加载页面后从 API 获取实际状态，不依赖前端缓存判定是否预约成功。
- 表单提交成功后展示成功结果；再次打开已使用链接只显示状态，不公开预约中的个人资料。

**验收条件**：

1. 公司能查看自己的预约信息，不能通过替换 ID 查看其他公司的预约。
2. 对应求职者能在自己的投递记录查看预约结果，其他求职者无权读取。
3. 公司、求职者和提交成功页面显示的预约时间一致。
4. 刷新或重启后预约结果保留，已使用链接不重新出现可提交表单。

## 第四阶段：验收与交付

### T14：权限、边界与页面交互检查

**功能**：统一检查角色隔离、异常反馈、文件和时间边界。

**实现方式**：

- 按“访客、管理员、公司 A、公司 B、求职者 A、求职者 B”逐项检查页面和直接 API 访问。
- 检查注册角色伪造、跨公司招聘修改、跨账号投递查看、简历下载及邀请管理越权。
- 检查 10 MB 文件边界、相同名称大小写与空格、关闭招聘时的投递、7 天到期边界和过去的预约时间。
- 检查各页的加载、空状态、重复点击、网络错误、会话失效及手机布局，修复发现的问题。

**验收条件**：

1. 权限检查覆盖后端接口，绕过页面也无法越权。
2. 关闭招聘、邀请过期和重复提交等限制以提交时后端状态为准。
3. 错误提示为中文且对应实际原因，不出现堆栈、密码或本地路径。
4. 主要流程可通过桌面和手机宽度页面完成。

### T15：自动化验收与浏览器全流程验证

**功能**：为完整业务流程提供可重复的验收证据。

**实现方式**：

- 使用真实浏览器执行“管理员建岗位 → 公司发布 → 求职者投递 → 公司查看和生成邀请 → 免登录预约 → 双方查看结果”。
