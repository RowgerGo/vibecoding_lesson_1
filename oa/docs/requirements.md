# OA 系统需求确认记录

## 已明确的范围

- 在 `oa/` 目录开发 OA 系统。
- 后端使用 Python 提供 API，前端使用 HTML，通过 API 与后端交互。
- 数据库使用本地 SQLite。
- 管理员可创建多个部门；部门为单级结构。
- 管理员在后台创建用户，并可将用户指定为某个部门的管理员。
- 普通用户和部门负责人必须且只能归属一个部门；系统管理员可以不属于任何部门。
- 用户可发起申请单，填写时间、标题、内容。
- 部门负责人可同意或拒绝申请单，拒绝必须填写理由。

## 已确认的方案

以下内容包含各轮需求确认及最新修订。

### 角色与权限

- 系统管理员负责管理全部部门和用户、查看全部申请单，默认不参与审批。
- “部门管理员”与“部门负责人”统一称为“部门负责人”。
- 每个部门只设一名负责人，负责人必须属于该部门。
- 部门负责人允许审批自己的申请，不需要系统管理员代审。
- 用户提交申请时选择指定的审批部门，由该部门负责人审批。审批权限取决于申请单的审批部门，不取决于申请人的所属部门。
- 普通用户只能查看自己的申请单。
- 部门负责人能查看自己的申请单，以及所有指定本部门审批的申请单。
- 本部门成员提交给其他部门的申请单，不因其所属部门而额外对本部门负责人可见。
- 系统管理员能查看全部申请单。
- 列表和详情遵循相同的数据权限。

### 申请单

- 用户填写申请事项时间、标题和内容，并选择审批部门；事项时间精确到日期。
- 系统另行记录提交时间。
- 填写后直接提交；状态为待审核、已同意、已拒绝。
- 提交后不能修改；被拒绝后可以重新发起一张申请单。
- 第一版不包含草稿、撤回和多级审批。

### 登录与技术方案

- 使用用户名、密码登录，不开放注册。
- 账号全部由系统管理员创建；首次启动时通过初始化命令创建系统管理员。
- 密码使用安全哈希保存。
- 第一版面向本机或小团队内网使用。
- 后端采用 FastAPI；前端采用原生 HTML、CSS、JavaScript；数据库采用 SQLite。
- 后端同时提供页面和 API。

### 停用与用户管理

- 系统管理员只处理管理工作，不发起申请。
- 用户和部门采用停用方式，保留历史数据；停用用户后禁止登录。
- 第一版不提供调部门、更换负责人和交接功能；现任负责人不允许停用。
- 部门内没有启用用户和待审核申请时，才允许停用部门。
- 仅已启用且已指定负责人的部门可作为审批部门，申请人可选择自己的部门或其他部门。
- 审批部门无负责人时不能接收申请；申请人所属部门无负责人不妨碍其选择其他可用部门提交申请。
- 第一版用户资料包括用户名、姓名、密码、部门、角色、启用状态。
- 用户名唯一，创建后不可修改。
- 用户可修改自己的密码，系统管理员可重置密码。
- 第一版不增加手机号、邮箱和找回密码功能。

### 第一版排除范围

- 用户明确要求不开发 Q9 中用户调部门、更换负责人以及相关历史申请归属处理功能。
