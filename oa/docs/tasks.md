## 验收基线

- Python FastAPI 提供 API 和静态页面；前端使用原生 HTML、CSS、JavaScript，通过同源 API 交互；数据保存在本地 SQLite。
- 用户的所属部门与申请单的审批部门是两个不同概念，审批权限由申请单的审批部门决定。
- 系统管理员负责管理及查看，不提交、不审批申请；部门负责人允许审批自己的申请。
- 不开发调部门、更换负责人、交接、草稿、撤回、提交后修改、多级审批、公开注册及找回密码。
- 所有权限必须在后端校验，隐藏页面按钮不能代替 API 权限控制。

## 逐项任务

### T01：项目骨架与本地启动

**功能**：建立可以独立运行的 OA 项目。

**实现方式**：

- 全部业务代码放在 `oa/`；建议划分 `app/`、`app/api/`、`app/services/`、`app/repositories/`、`app/static/`、`tests/` 和 `docs/`。
- 在 `requirements.txt` 声明依赖；配置数据库文件路径，使用 FastAPI 挂载页面与 API。
- 提供健康检查接口和统一 JSON 错误格式，区分未登录、无权限、参数错误及业务冲突。

**验收条件**：

- 在独立虚拟环境中按说明安装依赖后可启动服务，健康检查返回成功。
- HTML 页面与 API 由同一服务提供，静态资源路径可访问。
- 数据库、会话数据、真实密码、虚拟环境和缓存文件不会纳入版本控制。

### T02：SQLite 数据模型与初始化

**功能**：持久保存部门、用户、申请单和登录会话。

**实现方式**：

- 建立部门表：名称、启用状态、负责人用户引用。
- 建立用户表：唯一用户名、姓名、密码哈希、所属部门、系统管理员标记、启用状态；负责人身份从部门的负责人引用推导，避免重复维护角色。
- 建立申请单表：申请人、审批部门、事项日期、标题、内容、状态、提交时间、审批人、审批时间、拒绝理由。
- 建立会话表；开启 SQLite 外键约束，使用参数化 SQL 和事务，为常用查询建立索引。
- 通过初始化脚本创建表结构；提交时间、审批时间统一存储时刻，页面按北京时间展示。

**验收条件**：

- 空数据库可完成初始化，重复运行不清空已有数据；重启服务后数据仍存在。
- 重复用户名、无效外键及非管理员缺少所属部门均被拒绝。
- 每张申请单仅有一个申请人和一个审批部门；每个部门最多有一名负责人。
- 密码只保存哈希，业务记录不会因用户或部门停用而被删除。

### T03：首次创建系统管理员

**功能**：首次部署时创建管理账号。

**实现方式**：

- 提供命令行初始化入口，输入用户名、姓名、密码，密码采用隐藏输入。
- 使用安全密码哈希创建启用的系统管理员账号，允许不归属部门。
- 不提供默认通用密码或公开注册 API。

**验收条件**：

- 新数据库可通过命令创建管理员，随后可登录后台。
- 已有同名用户时返回明确错误，不覆盖账号或密码。
- 密码不会回显或写入日志，账号信息不会硬编码在仓库中。

### T04：登录、会话与密码管理

**功能**：登录、退出、查询当前身份、自助修改密码及管理员重置密码。

**实现方式**：

- 使用随机会话令牌和服务端会话存储，以 HttpOnly、SameSite Cookie 维持登录；配置会话有效期。
- 使用统一登录校验和角色权限依赖，验证账号启用状态；Cookie 会话的写操作校验 CSRF 令牌。
- 用户修改密码时校验原密码；管理员可为其他用户重置密码；修改或重置后使该用户已有会话失效。

**验收条件**：

- 正确账号密码可登录；错误密码、停用账号登录失败；响应不包含密码哈希和服务端会话数据。
- 退出或会话过期后不能继续调用受保护接口，停用账号的已有会话也不能继续使用。
- 原密码错误时不能修改密码；成功修改或重置后，旧密码及旧会话失效，新密码可登录。
- 普通用户及负责人不能重置他人密码；缺少有效 CSRF 令牌的写请求被拒绝。

### T05：部门管理与停用规则

**功能**：系统管理员创建、查看部门并管理启用状态。

**实现方式**：

- 提供管理员专用部门 API，采用单级结构，不增加父部门字段或部门树。
- 新部门初始无负责人，可先创建成员，再首次指定负责人。
- 停用时检查是否仍有启用用户或指定该部门审批的待审核申请；采用停用标记保留历史引用。

**验收条件**：

- 管理员可以创建多个同级部门；普通用户与负责人直接调用管理 API 也会被拒绝。
- 存在启用用户或待审核申请时，停用操作失败并说明原因；满足条件时可停用。
- 停用后部门及历史记录仍可查询，该部门不再出现在可选审批部门中。

### T06：用户创建、查询与启用状态管理

**功能**：管理员创建用户、查看用户及管理启用状态。

**实现方式**：

- 后台支持设置用户名、姓名、初始密码、部门、系统管理员角色及启用状态。
- 普通用户只能绑定一个启用部门；系统管理员可不选部门。
- 创建后不提供修改用户名、调部门的入口或 API 能力。
- 停用普通用户时使会话失效；若用户是现任负责人则拒绝停用。避免停用最后一个启用的系统管理员造成后台无法管理。

**验收条件**：

- 可创建普通用户和系统管理员；普通用户缺少部门、绑定多个部门或用户名重复时创建失败。
- 请求中尝试修改用户名或所属部门时被拒绝，不允许通过额外字段绕过限制。
- 普通用户停用后不能登录或使用原会话，历史申请仍保留；重新启用后可正常登录。
- 现任负责人不能被停用；最后一个启用的系统管理员不能被停用。

### T07：首次指定部门负责人

**功能**：为尚无负责人的部门指定一名负责人。

**实现方式**：

- 管理员从该部门已启用的普通用户中首次指定负责人。
- 后端校验所属部门、账号状态及现有负责人；在事务中完成指定，防止并发重复设置。
- 负责人身份自动影响权限，不提供移除、更换或交接入口。

**验收条件**：

- 可为无负责人的部门指定一名本部门启用用户，设置后其身份和审批权限生效。
- 指定其他部门用户、停用用户或系统管理员失败。
- 已有负责人时不能替换或清空；并发指定也不能产生两名负责人。

### T08：可选审批部门查询

**功能**：向申请人提供可接收申请的部门列表。

**实现方式**：

- 提供登录后可用的查询接口，仅返回启用且有启用负责人的部门。
- 查询范围覆盖所有可用部门，不按申请人的所属部门过滤。
- 返回部门名称与负责人姓名，供申请表单展示。

**验收条件**：

- 用户可选择自己部门或其他部门作为审批部门。
- 无负责人或已停用的部门不在选项中。
- 申请人所属部门无负责人时，仍可查询其他可用审批部门；无选项时页面给出明确提示。

### T09：提交申请单

**功能**：用户填写事项日期、标题、内容并指定审批部门，直接提交。

**实现方式**：

- 创建申请 API 从会话取得申请人身份，由服务器生成提交时间并设置“待审核”状态。
- 校验日期、非空标题、非空内容及目标部门可用性；全空白不视为有效输入。
- 普通用户和负责人可提交，系统管理员不能提交；创建后不提供修改、删除、撤回接口。

**验收条件**：

- 普通用户和负责人均可成功提交；负责人选择自己部门提交后仍可自审。
- 申请人所属部门没有负责人时，也能向其他可用部门提交。
- 缺少必填项、无效日期或指定无负责人的部门时，提交失败且不产生记录。
- 伪造申请人、状态、提交时间或审批信息不能生效；系统管理员直接调用创建 API 被拒绝。

### T10：申请单列表、详情与数据权限

**功能**：按角色查看申请列表、详情和处理结果。

**实现方式**：

- 提供分页列表及详情接口，可按状态筛选，并按提交时间倒序展示。
- 普通用户查询范围为自己提交的申请；负责人查询范围为自己的申请与指定本部门审批的申请之并集；系统管理员查询全部。
- 列表、详情和数量统计复用同一权限条件；返回申请人、审批部门、事项日期、状态及审批结果。

**验收条件**：

- 销售部用户提交给财务部的申请，申请人、财务部负责人、系统管理员可见；无其他身份关系的销售部负责人不可见。
- 负责人向其他部门提交的申请，自己仍可查看；自己的申请同时指定本部门时，列表不重复。
- 手工修改详情 ID、筛选参数、页码，不能看到越权记录或通过统计得知其数量。
- 完成审批后，详情能展示审批人、审批时间和拒绝理由（如有）。

### T11：同意、拒绝与审批记录

**功能**：目标部门负责人处理待审核申请，记录审批结果。

**实现方式**：

- 提供审批 API，校验操作者为申请单审批部门的现任负责人；允许申请人和审批人为同一人。
- 同意时记录结果；拒绝时强制填写非空理由。审批人和审批时间由后端生成。
- 使用事务和带“待审核”条件的更新保证一张单据只完成一次审批，已完成结果不可改写。

**验收条件**：

- 目标部门负责人可同意或拒绝，拒绝缺少理由或理由全空白时失败且仍为待审核。
- 负责人可以审批指定自己部门的本人申请；申请人的直属负责人若非目标部门负责人则不能审批。
- 普通用户、其他部门负责人、系统管理员均不能越权审批。
- 重复或并发审批只有一次成功，后续请求返回业务冲突；首次结果、审批人及审批时间保持不变。

### T12：前端公共页面与登录交互

**功能**：提供登录页、导航、退出及修改密码页面。

**实现方式**：

- 使用原生 HTML/CSS/JavaScript 建立公共布局和统一 `fetch` 请求封装，处理登录态、CSRF 令牌、加载状态及错误提示。
- 按当前身份显示管理、申请、审批导航；会话失效时引导回登录页。
- 用户输入内容通过文本方式渲染，避免将申请标题、内容、拒绝理由作为 HTML 执行。

**验收条件**：

- 不同角色登录后看到对应导航，退出后无法继续访问受保护数据。
- 登录失败、密码修改失败、网络异常均有可读提示，表单不会一直停留在提交中状态。
- 输入包含 HTML 或脚本片段的姓名、标题、内容及理由时，只显示为文本，不执行脚本。

### T13：申请与审批页面

**功能**：提供申请提交、我的申请、部门审批及申请详情页面。

**实现方式**：

- 提交表单包含事项日期、标题、内容、审批部门，并展示所选部门负责人。
- 我的申请展示本人记录；负责人另有部门审批列表，可筛选待审核、已同意、已拒绝。
- 详情页展示申请及审批记录；只有有权审批且处于待审核状态的记录展示审批操作，拒绝时填写理由。

**验收条件**：

- 用户可在浏览器完成跨部门提交，并在我的申请看到新记录。
- 目标部门负责人可从审批列表完成同意、拒绝及本人申请审批；结果刷新后仍保持。
- 已完成申请无再次审批入口，用户无修改、撤回、删除入口。
- 空列表、无可选部门、无权访问及提交失败均有明确提示；系统管理员不显示新建申请或审批按钮。

### T14：管理后台页面

**功能**：提供部门管理、用户管理和全局申请查询界面。

**实现方式**：

- 部门页支持创建、查看、启停及首次指定负责人。
- 用户页支持创建、查看、启停、重置密码，展示所属部门与实际角色。
- 全局申请页复用列表和详情接口，供管理员只读查看全部申请。

**验收条件**：

- 管理员可按“建部门 → 建成员 → 指定负责人”的顺序完成配置，并创建其他管理员。
- 后台能完成用户停用、启用与密码重置，业务限制失败时提示具体原因。
- 不出现调部门、更换负责人、交接和硬删除入口；已指定负责人的部门不能再次指定负责人。
- 普通用户和负责人直接打开后台地址或调用后台 API，也不能获得管理数据或执行操作。

### T15：API 集成测试与端到端验收

**功能**：验证核心流程、权限边界和历史持久性。

**实现方式**：

- 使用隔离的临时 SQLite 数据库执行 API 集成测试，准备管理员、两个部门负责人、普通用户及无负责人的部门。
- 测试聚焦跨部门审批、自审、越权访问、停用、状态转换与并发审批等核心业务。
- 使用真实浏览器完成管理员配置、用户申请、负责人审批和申请人查看结果的完整流程，记录实际结果。

**验收条件**：

- 下方“关键业务验收场景”全部通过，测试互不依赖执行顺序，不修改实际使用的数据库。
- 列表与详情越权、直接调用管理 API、伪造申请字段、空拒绝理由及重复审批均被正确拒绝。
- 浏览器联调通过，重启服务后部门、用户、申请内容和审批结果仍然存在。

### T16：启动说明与交付检查

**功能**：让项目可以由其他人在本地按文档独立启动和验收。

**实现方式**：

- 编写中文 `oa/README.md`，说明 Python 版本、依赖安装、数据库初始化、管理员创建、启动命令、访问地址和测试命令。
- 说明数据库文件位置、停止服务后的备份与恢复步骤，以及三种角色的操作流程和第一版限制。
- 汇总完成情况、实际测试结果与尚未解决的问题，不将未验证项标为通过。

**验收条件**：

- 新环境可按 README 从零启动，不依赖开发者本机绝对路径或预置账号。
- 按说明备份、恢复 SQLite 后，能够查询原有用户、申请与审批记录。
- 所有任务的完成状态有对应实现或验证记录，未完成内容明确列出。

## 关键业务验收场景

验收数据：系统管理员 A、销售部负责人 S、财务部负责人 F、销售部用户 U、销售部另一用户 V、无负责人的人事部用户 H；销售部与财务部均启用。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC01 | U 提交申请，指定财务部 | 创建待审核申请；U、F、A 可查看，S、V 不可查看；只有 F 可审批 |
| AC02 | S 提交申请，指定销售部，再由 S 审批 | 允许自审，记录审批人 S 和审批时间 |
| AC03 | S 提交申请，指定财务部 | S 可查看自己的申请但不能审批，F 可审批 |
| AC04 | F 拒绝申请但未填写理由或只输入空白 | 拒绝操作失败，申请仍为待审核 |
| AC05 | F 填写理由拒绝 U 的申请 | 状态为已拒绝，U 可查看理由；原单不可修改，U 可重新发起新单 |
| AC06 | H 提交申请，指定财务部 | 允许提交；人事部自身不在可选审批部门中 |
| AC07 | V 枚举他人申请详情 ID 或修改列表筛选参数 | 无法读取他人记录或获取越权记录数量 |
| AC08 | A 尝试提交或审批申请 | 拒绝操作，A 仍可查看全部申请及管理基础数据 |
| AC09 | A 停用普通用户 U | U 无法登录，原会话失效；历史申请和审批记录不删除 |
| AC10 | A 尝试停用 S、调动 U 或替换销售部负责人 | 全部拒绝，不改变既有部门归属及负责人 |
| AC11 | 并发两次审批同一张待审核申请 | 仅一次成功，另一请求冲突，结果不可覆盖 |
| AC12 | A 停用仍有启用用户或待审核申请的部门 | 拒绝停用并说明原因 |
| AC13 | A 停用一个无启用用户且无待审核申请的部门 | 停用成功，历史记录仍保留，不能作为新申请审批部门 |
| AC14 | 重启服务后重新登录查看已审批申请 | 内容、状态、审批人、审批时间、拒绝理由与重启前一致 |

## 建议交付顺序

1. T01—T04：服务、数据库和身份认证可用。
2. T05—T08：部门、用户、负责人和审批部门选项可用；T12 可在此阶段并行推进。
3. T09—T11：申请、查询、审批 API 闭环可用。
4. T13—T14：用户页面与管理后台完成联调。
5. T15—T16：通过验收并完成中文使用文档。
